# Termlume 发版操作规范

本规范规定从收到发版请求到交付验收的完整流程。适用于 `ingot-cloud/termlume`；执行时核实实际 remote、工作区、工作流及用户当前指令。自动打包实现见 [GitHub Release 自动打包](GITHUB_RELEASES.md)，签名与客户端机制见 [App 内更新](APP_UPDATES.md)，开发和本机更新约定见 [AGENTS.md](../AGENTS.md)。

## 任务范围与完成标准

用户要求发布指定版本后，持续完成准备、提交与推送、固定标签、发布 Release、跟进 Actions、核验公开产物和本机升级验收。已有明确授权直接沿用，不为同一动作反复确认。版本号或发布内容不明确时，先核对线上版本和本次变更，提出具体建议并补齐必要决定；期间继续可独立执行的检查与准备。

以下条件全部满足，才可报告“发版完成”：

- 发布标签、两平台构建审计和更新清单对应已核对的版本及同一提交。
- 相关原生检查，以及 Release 前置检查、macOS、Windows、附件上传作业均成功。
- GitHub Release 公开附件完整，摘要、签名、版本和下载地址核验通过。
- 本机实际安装并运行目标版本，正常启动；完成真实 App 内升级及升级后的检查更新。
- 工作区、主机、凭据和偏好保留，安装文件与已核验发布包一致。

“Release 页面已发布”“下载和验签通过”“App 能启动”分别只是其中一个阶段。遇到缺陷必须报告实际失败阶段，完成可独立执行的修复；不能把部分通过写成完整升级成功。

如果存在无法覆盖的步骤，明确记录原因、已有证据和待完成事项，按实际阶段交付；不能把缺失的本机升级验收写成已完成。预发布的自动发现限制也应单独说明。

普通修改、提交请求和发版请求按各自范围处理。修改规范不会自动触发新版本发布；用户只要求本机修复时，不自行发布新版本。

## 一、确认版本与发布提交

1. 阅读 `AGENTS.md`、本规范和相关工作流，检查 `git status`、分支、remote 及待发提交。保留用户已有修改，明确本次包含的内容，不顺带提交无关文件。
2. 核对 GitHub 已发布版本与远端标签，确认目标版本尚未发布。用户已指定版本时沿用该版本；未指定时结合 SemVer 和变更范围给出建议。不要仅根据 `package.json` 判断线上最新版本。
3. 按变更范围运行检查：Node 使用 `npm test`，界面使用 `npm run test:ui`，原生变更运行对应 Rust 测试；需要完整 macOS SSH/SFTP/Git 夹具时使用 `npm run tauri:test:macos`。已通过的同一变更检查无需无故重跑。
4. 按 Conventional Commits 提交相关修改，记录完整提交 SHA。推送到经核对的 `origin/main`，确认远端确实包含该 SHA。
5. 跟进拟发代码的 `Native tests`。Windows 和 macOS 都须通过；Windows 作业还包括离线 NSIS 构建、WebView2 分支和最终包审计。核对运行的 `head_sha`，不要引用其他提交的绿灯。未自动触发且需要原生验证时手动触发；仅文档提交复用既有运行代码的验证时，明确所引用的提交及等价范围。

当前版本由 `scripts/release-version.cjs` 在 Runner 中按标签同步五处文件：`package.json`、`package-lock.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock`。这不会向仓库回写提交。不要为了运行发版流程在用户工作副本随意降版本；本地复现版本同步时使用独立构建副本或明确记录本机版本变更。

## 二、检查签名配置

- 发布使用现有 `TAURI_SIGNING_PRIVATE_KEY` Actions Secret。私钥有密码时还需 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`；无密码时无需新增密码 Secret。
- 由工作流的 `Verify updater signing key` 签署随机挑战并核对内置公钥；已有配置正常时直接复用，不重复读取、粘贴或上传私钥。
- 首次上传或轮换密钥须获得对具体密钥、目标仓库和动作的明确授权。不要将私钥写入源码、发布说明、聊天、命令输出、日志、截图或构建产物，不为通过检查临时生成另一把钥匙。
- 应用代码签名和更新包签名是两件事。当前 macOS 试用版沿用临时签名，再签署更新包；采用正式签名后沿用正式身份。保持应用标识 `app.termlume.desktop` 和签名公钥连续性。
- 普通 `Native tests` 不接触生产签名私钥；发布流程仅把私钥传给密钥自检及打包签名步骤。

## 三、创建标签与 Release

先把下面的变量替换为本次已确认的真实值；仅在目标标签不存在且已获得发版授权时执行：

```sh
release_tag='vX.Y.Z'
release_commit='<已核对的完整提交 SHA>'
git ls-remote origin refs/heads/main "refs/tags/${release_tag}" "refs/tags/${release_tag}^{}"
git tag -a "$release_tag" "$release_commit" -m "Release $release_tag"
git push origin "refs/tags/${release_tag}"
```

标签必须解析到目标提交；已有标签应先核对其 SHA，不能自动覆盖或使用强制推送。版本格式及数字限制由 `release-version.cjs` 校验。

1. 使用可用的 GitHub 集成或 CLI；缺少所需能力时使用已登录浏览器。不要从浏览器提取 Cookie 或令牌来绕过正常授权。
2. 创建 Release，选择刚核对的现有标签；确认标题、版本说明和正式版/预发布状态。正式版正常标为 Latest；客户端只发现最新正式版，预发布不能按正式版自动发现来验收。
3. 发布说明写清用户可感知的变化、必要的升级兼容提示和正确安装包。检查自动生成的说明，避免遗漏已知限制或承诺尚未验证的结果。
4. 发布 Release 后记录链接。**仅推送 main、创建标签、保存草稿不会触发当前自动打包**；正常触发事件是 `release: published`。
5. 若仓库启用了 Immutable releases，按 [不可变发布说明](GITHUB_RELEASES.md#检查与补跑) 使用已有标签的草稿，先手动运行工作流、核验产物，再发布。先检查实际设置，不能等耗时构建完成才发现禁止追加附件。

创建、修改 Release 等外部动作完成后，观察保存后的实际页面并保留证据。若工具审批拦截，说明被拦截的具体动作和原因；在获得相应授权前，不通过其他接口执行同一被拒绝动作。

## 四、跟进 Actions 到结束

通过版本、事件和 `head_sha` 确认本次 `Release packages` 运行，记录运行 URL。持续关注以下四个作业：

| 作业 | 必须确认的结果 |
| --- | --- |
| `Validate release and tests` | 标签、版本及提交检查，签名密钥自检，Node 和界面回归通过 |
| `Build macos-arm64` | Rust 测试、构建、应用签名、包体及更新签名审计、无网络 Git 验证、保留产物成功 |
| `Build windows-x64` | Rust 测试、NSIS 构建、固定 WebView2 和内置工具审计、安装分支测试、更新签名及保留产物成功 |
| `Attach packages to GitHub Release` | 核验两平台同一提交、标签未移动、安装包上传和最后的更新清单上传全部成功 |

查看作业的最终 conclusion 及失败步骤；某一步构建完成或出现 Artifact，不代表整个作业成功。同时跟进尚未完成的相关 `Native tests`。

在当前任务持续检查，单次等待不超过 60 秒；仅在阶段性成功、失败、需要用户处理或完成时汇报。不要创建定时任务或提醒代替一次发版的跟进，也不要让用户自行盯后续结果。

## 五、核验公开产物

以工作流和 `scripts/package-release.cjs` 的 `specification` 为准。当前两平台共有 12 个自定义附件；GitHub 自动提供的两份 Source code 不计入安装产物。平台或命名扩展后按实际规格核对，不永久写死数量。

| 附件 | 数量 | 用途 |
| --- | --- | --- |
| `Termlume-VERSION-macOS-arm64-offline.zip` | 1 | 手动安装 macOS App |
| `Termlume-VERSION-macOS-arm64.app.tar.gz` 及 `.sig` | 2 | macOS App 内更新及签名 |
| `Termlume-VERSION-Windows-x64-setup.exe` 及 `.sig` | 2 | Windows 离线安装及 App 内更新 |
| `Termlume-VERSION-Windows-x64-offline.zip` | 1 | Windows 安装器和说明 |
| 两平台 `.build.json` | 2 | 版本、标签、提交、架构和审计记录 |
| 两平台 `.sha256` | 2 | 对应平台载荷校验清单 |
| `latest.json`、`SHA256SUMS` | 2 | 跨平台更新清单和完整文件摘要 |

验收步骤：

1. 查看公开 Release 附件列表，确认均上传成功、文件名和大小合理。检查实际下载端点，不能只依赖 Actions Artifact 列表。
2. 在独立临时目录下载清单、签名和审计文件。将 GitHub 服务端摘要、`SHA256SUMS`、平台摘要及 `.build.json` 中的大小和摘要互相核对；下载后的文件再次计算 SHA-256。
3. 实际下载两平台更新载荷，使用仓库内置公钥独立验签并核对签名绑定的目标版本。可调用 `scripts/updater-release.cjs` 导出的 `verify(data, signature, version)`；任何签名、版本或摘要不符都应停止安装。
4. 检查 `latest.json` 的版本、`darwin-aarch64` / `windows-x86_64` 目标、签名和下载 URL，确保指向本仓库同一版本的真实附件；审计提交须等于标签解析出的完整 SHA。
5. 确认更新清单在所有载荷上传完成后发布。Release 已创建但清单暂未就绪时，客户端应提示准备中；不能把准备中的状态当成永久失败，也不能把它当成可下载成功。
6. macOS 更新包解压后检查架构、版本、完整代码签名和文件内容；Windows 结合原生 CI 的安装器及资源审计核对。HTTP HEAD 和服务端摘要验证的 ZIP、实际完整下载验签的更新载荷，应在证据中区分。

## 六、本机 App 真实升级验收

本机升级是发版默认交付内容，不需在打包后再询问是否更新。当前实际路径为 `/Applications/Termlume.app`；执行前核对是否仍为用户使用的位置。

1. 记录升级前运行版本和进程，确认起点客户端支持此次更新；保留旧 App 备份，核实实际工作区路径。可记录用户数据文件摘要验证保留情况，不输出其内容或凭据。
2. 检查 SSH 会话、传输、文件编辑器、端口转发及 Git 同步。说明重启的实际影响，妥善处理正在进行的工作，不为了验收重置用户数据或直接终止活动任务。
3. 在已安装的原生 App 中打开「设置 → 关于与更新」，实际点击检查，确认新版本和说明；实际下载，观察进度及验签成功，再点击「重启并安装」。保留关键阶段的截图或状态证据。
4. 等待 App 自行退出并重启。先核对实际进程已经重新启动，再通过 UI 观察；注意“打开 App”工具可能主动启动程序，不能用它掩盖自动重启失败。
5. 确认新进程来自实际安装路径，UI 和安装文件中的版本均为目标版本；逐项比较安装文件与已下载、验签的 GitHub 发布包，并验证应用签名。
6. 检查原工作区、主机、凭据和偏好保留，重启后再次点击检查更新，应显示目标版本已是最新正式版。原生启动或交互验证不能用 Chrome 预览替代。

不要先手动安装目标版本再声称 App 内升级成功。若旧客户端没有更新功能、已是目标版本或更新入口自身有缺陷，明确说明前提，使用受支持的旧版验收客户端或安全隔离的验证环境；需要维护客户端引导时记录其来源和版本。手动替换、真实 App 内升级及各平台实机验收必须分别记录，不能用 macOS 实测推断 Windows 实机安装已验收。

应用运行代码需要修复时，按 `AGENTS.md` 重新构建、签名、安装本机 App 后继续验证。发版验收成功后，不再用落后的源码基础版本构建覆盖刚验收的正式 App；仅规范文档修改无需重装 App。

## 七、失败与修复发布

| 情况 | 处理方式 |
| --- | --- |
| 网络或 Runner 临时故障，发布源码未变 | 核实失败原因后补跑同一提交的失败作业或对应标签；继续等到完整结果 |
| 代码或打包脚本需要修改 | 先修复、补回归、完成相关检查与本机更新，形成可审阅提交，再确定包含修复的发布版本 |
| 版本已经公开，需要新补丁版本 | 提出具体下一版本及升级说明，获得对新版本的明确授权后发布；同一授权不重复询问 |
| 需要改已发布标签、用不同提交或内容替换已发布产物、补充历史 Release 说明 | 列出具体目标和影响，取得明确授权；原授权版本、提交和产物范围内的失败补跑沿用授权，不扩展到其他历史版本 |
| 签名或依赖摘要不符 | 保留错误证据，定位来源或配置问题，停止安装；不能关闭验签、放宽锁文件或接受任意 latest 文件来通过检查 |
| 发布成功，但真实 App 安装失败 | 报告安装失败及已通过阶段，保留用户数据，修复后重新进行真实升级；不能仅凭下载和验签宣布交付成功 |

**补跑不会自动使用新 main**：Re-run jobs 仍使用原运行提交；手动填写旧标签仍构建旧标签源码。修复提交推送成功不代表旧版本的构建已修复，不自动移动已发布标签。

需要新增授权时，先完成可以独立进行的修复、测试、本机更新和具体发布说明，再一次列明需授权的提交、版本、仓库及历史说明修改。自动审批拒绝后如实说明被拦截动作和理由，继续其他工作；明确授权到达后接着完成原任务。

## 八、交付证据与汇报

在忽略的 `dist/Termlume-vX.Y.Z-native-upgrade.build.json` 或对应交付记录中保存：

- 版本、标签、完整提交、Release 和 Actions URL、各作业最终结果。
- 附件集合、验证方法、大小与摘要，签名及清单版本核对结果。
- 实际安装路径、升级前后版本及进程、安装文件摘要和发布包一致性、代码签名验证。
- 用户数据保留结果、关键原生操作与截图、未完成或未覆盖的部分。不得包含私钥、令牌、密码或工作区明文。

最终回复直接说明发布结果、两平台及上传结果、本机实际版本和路径、真实升级是否完成、用户数据是否保留，提供 Release/Actions 链接。不要只回复“工作流已触发”。

## 已验证基线与故障经验

2026-11-15 的 [v0.2.4](https://github.com/ingot-cloud/termlume/releases/tag/v0.2.4) 对应提交 `6ec8603b32ac6be1153b6a521297a1022fdaf451`：[Native tests](https://github.com/ingot-cloud/termlume/actions/runs/43643100986) 两端通过，[Release packages](https://github.com/ingot-cloud/termlume/actions/runs/43643258602) 四个作业通过。12 个自定义附件及两平台更新载荷通过核验；本机修正后的维护客户端由标记版本 v0.2.2 经 App 内检查、下载、验签、安装和自动重启升级到 v0.2.4，安装文件与发布包一致，用户数据保留，升级后再次检查正常。这不表示 v0.2.2 官方发布包自带更新功能。

- `v0.2.3` 的下载和验签曾全部成功，真实点击安装才发现误拦截。HTML dialog 的关闭状态由 `open` 表示，`hidden` 默认仍为 false；回归必须使用真实 `show()` / `close()` 生命周期，不能用错误的属性模拟原生状态。v0.2.3 官方用户需先手动安装 v0.2.4 或后续修复版。
- Windows Tauri MockRuntime 库测试需声明 Common Controls v6。工作流在 Rust 测试步骤设置 `TERMLUME_TEST_WINDOWS_MANIFEST=1`，生产 App 构建继续使用正常 manifest。
- WebView2 等离线依赖须使用锁定来源并检查最终安装器内嵌文件；缓存或上游 latest 变化不能成为跳过 SHA-256/长度校验的理由。
- 工作区文件锁曾在 fork 到 exec 期间被子进程暂时继承；以可复现的并行测试定位并修复资源释放，不通过删除单实例保护或忽略失败用例掩盖问题。
